# 정적 분석과 포맷 분석

[상위 가이드로 돌아가기](../ANALYSIS_GUIDE.md)

## 분석 대상 식별

분석 전에 `analytics/result/disc/targets.md`에 다음을 기록하고 `analytics/result/INDEX.md`에서 연결한다.

```text
게임: <title>
플랫폼: <platform>
지역/판본: <region/edition/serial>
매체: <BIN/CUE/ISO/ROM 등>
파일: <main executable or data file>
크기: <bytes>
SHA-256: <hash>
Ghidra 언어: <실제 선택값>
이미지 베이스: <address>
추출 도구와 버전: <tool/version>
비고: 원본 또는 기존 참조 패치 적용본
```

동일한 이름의 파일이라도 해시가 다르면 별도 대상으로 취급한다. AI는 해시가 확인되지 않은 두 파일을 같은 판본이라고 단정하지 않는다.

## 주소 표기 규칙

주소를 기록할 때 반드시 종류를 접두어로 표시한다.

| 표기 | 의미 | 예시 |
|---|---|---|
| `VA` | 실행 시 가상/RAM 주소 | `VA:0x80041230` |
| `GHA` | Ghidra 프로그램 주소 | `GHA:0x80041230` |
| `FO` | 개별 파일 내부 오프셋 | `FO:0x0012A430` |
| `DO` | BIN/ISO 전체 바이트 오프셋 | `DO:0x18F24000` |
| `LBA` | 디스크 논리 블록 번호 | `LBA:123456` |
| `RO` | 압축 해제 또는 런타임 버퍼 상대 오프셋 | `RO:0x340` |

PS1 데이터 트랙의 raw BIN은 섹터당 2352바이트일 수 있고, 사용자 데이터는 모드에 따라 별도 위치와 크기를 가진다. PS2 ISO는 일반적으로 2048바이트 논리 섹터를 사용한다. 변환식을 적용하기 전에 이미지 형식과 트랙 구성을 확인한다.

주소 변환을 문서화할 때는 계산식과 전제도 함께 기록한다.

```text
관찰: 파일 A의 FO:0x120은 ISO의 LBA:34567에 포함됨
전제: 2048-byte sector, 파일 시작 LBA:34567
계산: DO = (34567 * 2048) + 0x120
검증: ISO 바이트와 추출 파일의 32바이트 구간이 일치함
```

## 증거 수준

모든 주요 발견은 다음 상태 중 하나로 표시한다.

### `[FACT]` 확정

재현 가능한 절차로 확정된 사실이다. 해시, 파일 크기와 직접 읽은 헤더처럼 의미 해석이 없는 결정적 측정은 한 가지 재현 절차로 충분하다. 함수 역할이나 데이터 의미처럼 해석이 포함된 주장은 독립적인 두 근거, 왕복 테스트 또는 정적·동적 분석의 일치를 요구한다.

### `[OBSERVED]` 관찰

도구로 직접 확인했지만 의미는 아직 확정되지 않은 값이나 동작이다.

### `[LIKELY]` 유력

여러 근거가 일치하지만 동적 검증이나 추가 표본이 필요한 해석이다.

### `[HYPOTHESIS]` 가설

조사 방향을 잡기 위한 임시 설명이다. 반증 가능성과 다음 실험을 반드시 적는다.

### `[UNKNOWN]` 미확인

현재 자료로 판단할 수 없거나 서로 충돌하는 상태다.

### `[SUPERSEDED]` 대체됨

작성 당시에는 유효했지만 후속 분석으로 잘못되었거나 더 정확한 결론으로 대체된 기록이다. 과거 판단이 반복되지 않도록 삭제하지 않는다. 대체 시각, 대체 결론의 파일+anchor 링크와 대체 이유를 반드시 기록한다.

모든 주요 발견에는 `recorded_at`을 기록한다. 런타임에서 실제로 관찰한 시각이 다르면 `observed_at`, 덤프나 스크린샷을 수집한 시각은 `captured_at`, 기록을 대체한 시각은 `superseded_at`으로 구분한다. Git 커밋 시간은 분석 시각을 대신하지 않는다.

결과 문서의 전체 형식은 [analysis-result.sample.md](samples/analysis-result.sample.md)를 시작점으로 사용한다.

권장 상태 흐름은 `UNKNOWN → HYPOTHESIS → LIKELY → FACT`다. 직접 관찰한 원시 현상은 어느 단계에서든 `OBSERVED`로 별도 기록하고 다른 주장의 근거로 연결한다. 반증되거나 더 정확한 주장으로 대체되면 기존 항목을 `SUPERSEDED`로 바꾸며, `SUPERSEDED`는 삭제하거나 다시 활성화하지 않는다. 상태 변경에는 근거와 시각을 기록한다.

예시:

```text
[OBSERVED] VA:0x80041230은 스크립트에서 16비트 값을 읽고
VA:0x8009B120을 호출한다.

[LIKELY] 읽은 값은 음성 ID이고 VA:0x8009B120은 음성 로더다.
근거: 호출 직후 오디오 관련 함수가 호출되며 기존 분석 기록과 일치한다.

[HYPOTHESIS] 0xffff는 음성 정지 명령일 수 있다.
반증 가능성: 누락 음성을 뜻하는 센티널일 수 있다.
다음 실험: 에뮬레이터에서 인자를 0xffff로 변경하고 SPU 호출을 기록한다.

[SUPERSEDED] 패키지가 디스크에 직접 암호화되어 저장된다는 추정.
recorded_at: 2026-07-10T18:00:00+09:00
superseded_at: 2026-07-16T20:40:00+09:00
superseded_by: runtime/battle-package-loading.md#current-loading-path
이유: 후속 워치포인트에서 중간 조립 단계를 확인했다.
```

## 함수 분석 절차

AI는 함수 하나를 분석할 때 다음 순서를 따른다.

1. 대상 파일, 해시, 판본과 함수 주소를 확인한다.
2. Ghidra 디컴파일 코드와 실제 어셈블리를 함께 확보한다.
3. 함수 호출자, 피호출자, 문자열 및 전역 데이터 참조를 수집한다.
4. 입력, 출력, 부작용과 오류 경로를 구분한다.
5. 구조체 오프셋과 테이블 접근 패턴을 기록한다.
6. 함수 역할에 대해 1~3개의 가능한 가설을 세운다.
7. 각 가설의 근거와 반증 가능성을 적는다.
8. 최소 비용으로 구분 가능한 정적 또는 동적 실험을 제안한다.
9. 검증 전에는 함수명을 확정적인 의미로 변경하지 않는다.
10. 확정 후 함수명, 자료형, 주석과 분석 문서를 함께 갱신한다.

함수 분석 보고서 형식:

```markdown
### VA:0x80041230 / FUN_80041230

- 대상: `<filename>`, SHA-256 `<hash>`
- 현재 상태: `[LIKELY]`
- 제안 이름: `dispatch_script_opcode`
- 호출자: `VA:...`, `VA:...`
- 피호출자: `VA:...`
- 입력: `a0 = script context` 추정
- 출력: `v0 = status` 추정
- 부작용: script PC 변경, 함수 포인터 간접 호출
- 핵심 근거: 첫 바이트를 4배하여 주소 테이블을 참조
- 불확실성: 테이블 항목 수와 범위 검사 의미 미확인
- 다음 검증: opcode 값을 바꾸고 간접 호출 목적지 기록
```

## 구조체와 자료형 복원

1. 단일 함수만 보고 구조체를 확정하지 않는다.
2. 같은 베이스 포인터의 오프셋 접근을 여러 함수에서 모은다.
3. 읽기/쓰기 크기, 정렬, 초기화 함수와 할당 크기를 확인한다.
4. 필드 이름은 역할이 검증되기 전까지 중립적으로 짓는다.
5. 겹치는 접근이 있으면 union, 비트 필드 또는 잘못된 함수 시그니처 가능성을 검토한다.
6. 구조체 변경 전후 디컴파일 결과가 실제 어셈블리와 일치하는지 확인한다.

초기에는 다음처럼 보수적으로 명명한다.

```c
struct TextContextCandidate {
    uint32_t field_00;
    uint16_t field_04;
    uint16_t field_06;
    const uint8_t *script_ptr;  // [LIKELY]
};
```

`field_04`를 `glyphIndex`처럼 구체적인 이름으로 바꾸려면 사용처 또는 런타임 값으로 검증해야 한다.

## 원본과 패치본 비교

원본과 기존 번역 패치 적용본을 비교할 때 전체 이미지의 단순 바이트 차이만 보고 의미를 단정하지 않는다.

기존 patch EXE나 installer는 실행하지 않고 overlay·resource·record stream의 정적 분석을 우선한다. 실행이 필요한 경우 [알 수 없는 실행 파일 안전 규칙](quality-operations.md#알-수-없는-실행-파일-안전-규칙)을 따른다.

권장 순서:

1. 이미지와 주요 파일의 크기 및 SHA-256을 기록한다.
2. 파일 시스템 목록, 파일 시작 LBA와 크기를 비교한다.
3. 변경 파일을 식별한다.
4. 변경 파일 내부에서 연속 변경 구간을 계산한다.
5. 실행 파일 변경은 Ghidra 함수와 데이터 주소에 대응시킨다.
6. 데이터 변경은 문자열, 폰트, 스크립트, 압축 및 재배치로 분류한다.
7. 코드 변경과 데이터 변경 사이의 참조 관계를 확인한다.
8. 패치가 새 데이터를 추가한 경우 포인터, 크기, LBA 또는 할당량 변경을 추적한다.

비교 결과 형식:

```text
변경 ID: <PROJECT>-REF-0012
원본 파일: MAIN.EXE / SHA-256 ...
패치 파일: MAIN.EXE / SHA-256 ...
원본 범위: FO:0x...
패치 범위: FO:0x...
대응 VA: VA:0x...
분류: 코드 / 데이터 / 재배치 / 미확인
상태: [LIKELY]
설명: 문자 코드 범위 검사 상한 변경 가능성
검증: 해당 분기에서 브레이크포인트 후 한중 문자 입력 비교
```

## 포맷 분석과 도구 작성

독자 포맷을 분석할 때 AI는 다음 규칙을 따른다.

1. 매직, 버전, 엔디언, 헤더 크기와 정렬을 먼저 확인한다.
2. 읽기 함수의 접근 순서를 실제 어셈블리와 비교한다.
3. 모든 숫자 필드에 크기, 부호, 엔디언과 기준점을 기록한다.
4. 오프셋이 파일 시작, 섹션 시작 또는 런타임 베이스 중 무엇을 기준으로 하는지 확인한다.
5. 정상 파일 하나만으로 포맷을 확정하지 않는다.
6. 빈 항목, 최대 크기, 중복 오프셋, 잘린 파일과 잘못된 값도 테스트한다.
7. 파서는 입력 범위를 검사하고 오류 위치를 명확하게 보고해야 한다.
8. 추출기와 재빌더는 가능한 경우 결정적 출력과 왕복 테스트를 지원한다.

필수 왕복 테스트:

```text
원본 → 파싱 → 변경 없이 재빌드 → 원본과 바이트 비교
```

재빌드가 원본과 일치하지 않는 포맷이라면 정렬, 패딩, 압축의 결정성 차이를 문서화하고 의미적으로 동일한지 별도 검증한다.
